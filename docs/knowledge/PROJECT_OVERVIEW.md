# Towards Victory — Project Overview

## Mod Identity

- **Mod Name:** Towards Victory (胜利条件)
- **Mod ID:** `eu5mp.towards_victory`
- **Version:** 0.1.0
- **Target:** EU5 `1.*.*`
- **Status:** In Development — All 6 Victory paths fully implemented: Conquest, Prosperity, Trade, Diplomatic, Cultural, and Scientific
- **Language:** English + Simplified Chinese

## Development Policy

Towards Victory is an unreleased v0.1.0 project. No saved-game compatibility, published
mod-version compatibility, or public API compatibility is required. Active code and data
should represent one current architecture. When a refactor improves clarity, performance,
generator ownership, or data flow, update all producers and consumers to the new shape and
delete stale branches rather than keeping migrations, aliases, duplicate paths, wrapper
entry points, or defensive fallbacks for old internal states. Existing helpers should be
reused only when they fit the current scope/lifecycle/data model; otherwise split, replace,
or remove them.

Existing mentions of compatibility launchers, legacy schema blocks, migrated old variables,
startup/migration repair, or fields retained for compatibility describe cleanup debt, not
contracts. When touching those areas, convert callers/data to the current shape and remove
the old path instead of preserving the compatibility layer.

Towards Victory adds 6 generalized victory paths to EU5: Conquest, Prosperity, Trade, Diplomatic, Cultural, and Scientific. Each path has 5 milestone nodes, and each milestone offers 3 independent permanent reward modifiers selected through the reward buttons. Reaching a milestone unlocks its reward slot and fires a popup event for notification/unlock-only side effects; permanent buffs are applied only through the generated three-choice reward buttons. Each path's progress is initially gated by `tv_<path>_victory_enabled` and normally unlocks independently only after that path's IO establishment flow is complete; Trade and Diplomatic Victory can also unlock immediately when a country joins another country's Trade League or Diplomatic Alliance. The main victory situation is a generated single-path page with a six-button top switcher backed by the player country variable `tv_victory_selected_path`; disabled paths show a three-step establishment card, while enabled paths show the per-path overview card with a concept-linked title, playstyle bullet, progress-formula bullet, progress and reward cards, and a per-path global top-five leaderboard.

IO establishment is data-driven by `data/io_establishment.yaml`. Every path uses the same three-step lifecycle: a monthly pulse completes the basic requirement flag, fires a player guidance event, and refreshes the headquarters-built cache; the guidance event or the capital-only `select_trigger` action can start that path's 300-ducat headquarters with themed maintenance goods; headquarters completion is marked from the building `on_construction_ended` hook and fires a second guidance event to appoint the chief; and the appoint-chief action initializes the country leader variable, applies the chief modifier, creates the matching non-unique IO, sets `tv_<path>_victory_enabled = 1`, fires the generated establishment event, and immediately refreshes that path's victory progress. AI countries use the same generated build-HQ and appoint-chief actions through `generic_action_ai_lists`, action-native `ai_tick`, and `ai_will_do`; the monthly pulse no longer simulates those action effects. Diplomatic AI countries complete step 1 at 10 diplomatic reputation like players, but only execute the step-2 headquarters build action at 20 diplomatic reputation or higher while fewer than 10 Diplomatic Alliances already exist worldwide; Trade AI countries complete step 1 at 50 monthly trade income like players, but only execute the step-2 headquarters build action at 100 monthly trade income or higher and while fewer than 10 Trade League leader countries exist globally. The step-3 appoint-chief actions have no extra diplomatic-reputation or trade-income gate once the headquarters exists, though Trade AI still obeys the global Trade League cap.

Trade League law update: `data/trade_league_laws.yaml` now drives generated `tv_trade_league_laws.txt`, adding five three-level vote-based laws: Customs Union, Maritime Convoys, Merchant Courts, Staple Monopolies, and Investment Code. Each level-1 policy trades roughly one benefit package for one cost, level 2 gives about 1.5x the same benefits for the same cost, and level 3 gives about 3x the same benefits for two distinct costs. AI policy vote bias uses base weights 200/100/0 for levels 1/2/3; levels 2/3 also scale from opinion of the leader (-50..+50 / -100..+100), leader diplomatic reputation (+2/+5 per point), and leader monthly trade income (+5/+10 per 100 income). Trade League law votes use the Grand Merchant law-change availability trigger and mutually block commercial-intelligence and monopoly maintenance work; Trade Chain maintenance is leader-country state and no longer occupies the Grand Merchant.

The **Conquest Victory** path (征服胜利) is fully implemented: 5 triggers, 15 selectable reward modifiers, 5 events, and localization in English and Simplified Chinese. Score = direct locations + 0.5 × subject-or-below locations; thresholds at 200 / 400 / 600 / 1200 / 2500.

The **Prosperity Victory** path (繁荣胜利) is fully implemented: 5 triggers, 15 selectable reward modifiers, 5 events, and localization in English and Simplified Chinese. Score = (total_population + Σdev + country_tax_base) × 50 / (N + 50) × (1 + stability/100) × (gov_power/100), where N = num_owned_locations and gov_power = legitimacy/republican_tradition/devotion/tribal_cohesion/horde_unity by government type. The 50N/(N+50) effective scale term provides stronger diminishing returns on country size. Updated yearly; thresholds at 2,000 / 3,000 / 5,000 / 7,000 / 11,000 (provisional, calibrate after playtesting).

**Prosperity main mechanic:** Establishing the Prosperity IO creates the **Engineering Department IO** (`tv_engineering_department`), a non-unique founder-only IO with no parliament tab and no automatic leader election. Its appointed character leader is the **Great Engineer**, stored on the leader country as `tv_great_engineer_char` and managed by generated Appoint/Remove/Change leader actions. Wonder Construction implements **Conception, Debate, Survey, Organization, Logistics, Construction, Ceremony, and Finalization** for 54 universal wonder types, all managed through the same generated mechanics layer from `data/wonders.yaml` and `data/wonder_final_buildings.yaml + data/wonder_generic_rituals.yaml + data/wonder_base_modifiers.yaml + data/wonder_site_rules.yaml`: Sacred Mountain Complex through Pirate Port, spanning civil production, military defense, civic timekeeping, arts, diplomacy, law, commerce, finance, industry, maritime trade, civilizational memory, prehistoric ritual, cathedral, monastic, and urban building-cap expansion, civic tower, sculpture-group, coastal-artillery, naval-school, colonial-company, assembly-hall, mobile-fortress, ancient-ruins, summer-palace, public-credit/state-bank, and corsair/privateering-port themes. Appointing a Great Engineer rebuilds the country's feasible proposal deck from owned terrain/city/port/infrastructure/mining/urban-capital conditions, then rolls or restores three simultaneous proposal slots on that engineer. The overview shows three wonder buttons, each labeled by size icon and wonder name; selecting one changes the Great Engineer's short pitch to that wonder's size-aware summary. Accepting locks the currently selected wonder and enters debate, while refuting or bribing refreshes all three proposal slots at once; rejected proposals are removed from the current deck, and if rejection empties the feasible deck the country immediately rebuilds the feasible list and rolls again. Debate uses the Engineering Department IO variable `tv_wonder_domestic_support` (0-200): estate demands for Nobles, Burghers, and Clergy can be accepted for +20 support through `tv_change_wonder_domestic_support_effect`, whose effect localization renders the IO variable change. Refuting or bribing estate demands does not exclude that agenda type. Demand types include the baseline privilege/tax/levy/policy agenda set plus resource-loss demands for 10 Prestige, 7 Stability, 5 Legitimacy, 5% loyalty from the other two estates, 2.5% inflation, one cabinet member, one artist, or one artwork; the cabinet/artist/artwork demands reroll matching slots after execution so two estates cannot keep pointing at a just-consumed scarce target. Monthly debate events can swing support by +/-20, and the debate can end at 100 support. After debate ends, support decays by 1 per month until the wonder is finalized; reaching 0 before finalization automatically declares construction complete if at least one wonder level is complete and the project can enter ceremony, otherwise it forces project collapse. Abandoning or forced collapse applies upper-estate satisfaction penalties, removes the Great Engineer, costs 20 Prestige, and resets wonder project state.

After debate, the player starts a location-select survey through `tv_wonder_start_survey`. Valid sites depend on the locked wonder type: Sacred Mountain uses hills/plateau/mountains; Triumphal Axis uses city/megalopolis; Great Port and Great Lighthouse use ports; Giant Necropolis uses hills or adjacency to city/town; Hydraulic Workshop uses land; Mining City now requires a mineral-producing raw material site (iron, copper, tin, lead, silver, gold, or marble). Fresh survey and construction candidate checks no longer exclude locations that already contain other TV wonder intermediate, module, or final buildings, but they do exclude the same wonder's existing module/helper/final buildings so resume and upgrade projects stay on the saved priority-candidate path. Priority resume/upgrade projects are valid when the saved site still matches the current wonder's base site rules and either has that wonder's module/helper building or has a final building below the location's stored scale tier. Survey progress is the Engineering Department IO variable `tv_wonder_survey_progress`; each monthly tick adds 0.1 times the Great Engineer's MIL and can fire one survey event from a single random roll. The country tracks the current survey site and three visible competence values: `tv_wonder_scale_competence`, `tv_wonder_logistics_competence`, and `tv_wonder_organization_competence`, initialized at 0 when a new survey begins. At survey start, hidden target competence values are precomputed from 25 base competence, each field's random 0-25 roll, the site preference bonus, and up to 10 from the Great Engineer's ADM; the visible competence values then rise by fixed monthly increments until completion. Monthly survey events can still raise or lower one visible competence by 5, or offer resource tradeoffs for +5. Site preference bonuses use: Sacred Mountain topography/vegetation (mountains +15, plateau +7.5, hills +0, forest +10, woods +5); Triumphal Axis development (0-100 maps linearly to 0-20) plus +5 for megalopolis; Great Port and Great Lighthouse harbor capacity (`harbor_suitability`, 0-100% maps linearly to 0-25, capped above 100%); Giant Necropolis hills +15, adjacent city +10 or adjacent town +5; Hydraulic Workshop total local building levels 0-100 maps linearly to 0-25; Mining City development 0-100 maps linearly to 0-20, plus +5 when the mineral site is a rural settlement. The survey card's Suitability Knowledge section always shows the current wonder's country-scoped build/location trigger through the normal trigger condition list; its suitability rows remain visible as placeholders until surveys reveal them, and revealed rows display actual-vs-maximum preference bonus as `?/+x` before the current site survey completes or `+y/+x` after completion. Each fresh completed survey increments the country-scoped `tv_wonder_suitability_revealed` variable map entry keyed by the wonder mechanic id up to that mechanic's row count, so unique wonders and their prototype share reveal progress. Actual suitability row values are stored in the country-scoped `tv_wonder_suitability_actual` map by `mechanic_id * 10 + row`, then mirrored into `tv_wonder_suitability_current_actual_<row>` for the selected wonder's GUI. Completed survey results are stored on the location in `tv_wonder_surveyed`, `tv_wonder_survey_scale_competence`, `tv_wonder_survey_logistics_competence`, `tv_wonder_survey_organization_competence`, `tv_wonder_survey_scale_tier`, and `tv_wonder_survey_suitability_actual` maps keyed by wonder id or suitability composite row id; selecting an already surveyed site restores the stored result instead of restarting progress and does not advance suitability knowledge. Scale competence maps to maximum wonder construction level using thresholds 20/40/60/80/100, with level 6 requiring 100% competence; Organization Competence maps linearly from 0-100% to a 0-20 Wonder Worksite level cap; Logistics Competence maps linearly from 0-100% to a 50%-150% monthly construction progress multiplier. The UI displays these three effects as concise three-line text blocks with the numeric value on the middle line. `tv_wonder_select_construction_site` confirms the completed survey site, grants 0/20/40 domestic support from the average result (<50 / 50-74 / >=75), and unlocks organization, logistics, and construction.

The generated site rules cover all generic wonders: University City excludes rural settlements and favors cities plus local literacy; Sky Dome Grand Temple requires state-religion population and favors monasteries, cathedrals, and higher state-religion share; Giant Tower Temple has no hard site limit and uses the same religious preference profile; River Extension requires a river site and favors development, bridges, and adjacent River Extensions; National Shipyard requires coast and favors harbor suitability plus development; Star Fortress City excludes rural settlements and favors mountains, plateau, forts, and cities; Great Wall excludes cities and favors mountains, plateau, forts, and rural settlements; Giant Armory excludes rural settlements and favors existing armory infrastructure, cities, and development; Library of Nation is capital-only and favors development, cities, and megalopolises; National Bank requires the capital, a city, or a megalopolis and favors capitals, urban rank, and development; Pirate Port requires a port and favors harbor suitability, existing fortifications, and city/megalopolis sites.

Wonder scale rules are size-driven. Small wonders may be built more than once, but their inherited `base_modifiers` country effects may only use `monthly_towards_*` value-movement modifiers. Medium and large wonders cannot start a second fresh same-type project for the same country, while same-site expansion remains allowed, and their base country modifier keys are unrestricted. `buildings.*.final_local`, generic ritual modifiers, and unique ritual/ceremony modifiers are outside this base-effect restriction. Unique wonders use the same size rule as their inherited generic prototype; current unique data also fixes one `location` and one ceremony style, so unique wonders are effectively single-site.

Shared Engineering Department wonder mechanics are now split by data responsibility: `data/wonder_site_rules.yaml` owns site triggers, hidden preference scripts, and derived suitability rows; `data/wonder_base_modifiers.yaml` owns level-scaled country/base effects; `data/wonder_final_buildings.yaml` owns final local modifiers, maintenance, and final-building attributes; `data/wonder_generic_rituals.yaml` owns the three generic ritual branches; and `data/wonder_design_notes.yaml` keeps non-runtime design notes. These files feed final building local effects and maintenance, national base effects excluding Great Power Score, generic ritual data, proposal/survey/index bridges, site-rule dispatch, generated concepts/localization/GUI text, generated ceremony requirement/effect detail panels, finalization bridges, and the generated `tv_wonder_index_effects.txt` variable-map index. `buildings.*.final_local` is the shared authored local-effect map for final wonder buildings; it is not keyed by final branch, so the final-building generator applies the same local-effect package to all three generic final branches, and unique final buildings inherit that prototype package through their strict `base_effect_multiplier = 2`. Final building `modifier` blocks include only the default local culture values, the authored local-effect package, and the wonder's national base effects as display-only data. Actual base national/global effects are generated in `src/in_game/common/auto_modifiers/tv_engineering_department_wonder_mechanics_auto_modifiers.txt` as level-gated Country Auto modifiers. Generated country and location static mirrors support Engineering Department and location-window `ShowModifierEffect` displays through id-based keys; real ritual country effects use existing ritual static modifiers and are granted at ritual completion. All generic wonders use the same three-style ritual framework: style 1 starts a one-year national burden and later grants a weaker permanent blessing static modifier, style 2 constructs a wonder-specific auxiliary annex building with unique local effects and +50% local estate power for the wonder's estate, and style 3 consumes one fixed decoration cost branch (one artwork, `scaled_gold = 5`, or 50 Prestige) for a large one-time reward. Display-only scripted effects feed the ceremony UI's original-style effect tooltip lists; style-2 annex rewards use generated location static modifiers in `src/main_menu/common/static_modifiers/` so the local modifier package can be shown through `add_location_modifier`. Generic ritual confirmation is split across `tv_wonder_confirm_ceremony`, `tv_wonder_confirm_ceremony_scaled_gold`, and `tv_wonder_confirm_ceremony_prestige`; unique wonders still auto-lock style 1 on construction completion, and their normalized `ritual` schema from `data/unique_wonders.yaml` can complete through configured listeners plus `completion_trigger_script`, optional `snapshot_effect_script` / `progress_effect_script`, and branch-specific runtime variables.

`data/unique_wonders.yaml` defines the unique historical wonder layer (123 entries, ids 101-223). Each entry maps to an existing generic wonder through `base_key`, inherits the generic size, site rules, derived suitability rows, buildings, and base country effect shape, then applies a 2x base-effect multiplier, a fixed `location`, an `initial_level` value (0 means absent at game start, 1-6 means constructed at that level), unique concept/name/flavor/history-intro/image prompt, and one unique ritual definition through either the legacy `ceremony` block or the newer `ritual` block. The **Trade Victory** path (贸易胜利) is fully implemented with a Trade League layer: 5 triggers, 15 selectable reward modifiers, 5 events, and localization in English and Simplified Chinese. Trade League monopoly tracking and actions are generated from the pure goods list in `data/trade_league_goods.yaml`, with Trade Chain configuration in `data/trade_chain.yaml`. Per good, the final monopoly percentage, monopoly type, stage, origin/transit/consumer control percentages, representative market detail variables, persistent virtual-demand, virtual-supply, embargo state, and Trade Chain bargaining demand state are stored on the Trade League `leader_country`, not in the IO type `variables = {}` block; initializing thousands of IO variables caused severe in-game stutter. The generated Trade League IO type also avoids an IO `monthly_effect`; Trade League maintenance is routed through registered monthly and yearly country pulses in `data/pulse_registry.yaml` plus the manual `tv_trade_league_on_action.txt` bridge. Grand Merchant work is mutually exclusive through `tv_trade_league_triggers.txt`: commercial intelligence (`tv_trade_commercial_intelligence_active`), active `resolution:policy_vote`, and monopoly maintenance availability block one another as appropriate. Trade Chain is no longer a Grand Merchant busy state. When none of those implemented busy states is active, `tv_trade_league_assist_caravans_modifier` applies as a leader-country Country Auto modifier for +10% merchant maintenance efficiency and is shown as the header action-card fallback; the planned promote-monopoly action has no display state yet and is not surfaced.

Trade Chain is a 20-slot persistent leader-country market chain. Canonical state uses `tv_trade_chain_market_by_slot` as a variable map keyed by slot number with market-scope values, plus the ordered `tv_trade_chain_markets` variable list for GUI iteration; `tv_trade_chain_count` includes the capital node. Slot 1 is always the current capital market. `tv_trade_add_chain_node` selects one market at a time; the selector and final effect require trade range, no duplicate existing chain node, and for the next node's market center to be strictly closer to the previous node's market center than to any other existing chain node's center. Creation, monthly maintenance, and capital-change handling ensure or rebuild slot 1 from the current capital market. The `on_capital_moved` bridge resets the chain only when the old and new capital markets differ, clears old permanent temporary bargaining demands, and notifies human players through `tv_trade_league_chain.1`. Monthly maintenance computes `flow = n / Σ(1 / market_capacity)`, sets flow to 0 if any chain market has non-positive leader capacity, measures endpoint distance from the capital market center to the terminal market center, and stores `strength = floor(length × flow / 1000)`. Strength at 100 grants `tv_trade_chain_medium_modifier` (+10% merchant maintenance efficiency); strength at 1000 also grants `tv_trade_chain_strong_modifier` (+20% trade advantage). Each point of strength contributes 0.01% display-only `tv_trade_bargaining_efficiency`; the GUI dynamically resolves `ShowModifierEffect(Concatenate('tv_trade_chain_strength_display_', strength_display))` against generated `tv_trade_chain_strength_display_0..20000` static modifiers instead of emitting one display widget per strength. Each month the chain clears old permanent temporary `tv_trade_chain_bargaining_demand_<good>` demands, then clears and rebuilds `tv_trade_chain_demand_slot_1..20` variable maps keyed by `goods:<id>` scope. From back to front it records exports from node n to node n-1 and adds `trade_volume × strength × 0.0001` demand to every preceding node 1..n-1 for that good.

Monopoly tracking uses an annual global good refresh, yearly per-league full recalculation, and monthly slot-only recalculation. The annual global refresh writes keyed `global_variable_map` entries for each good index: global production, global consumption, representative origin/transit/consumer markets, representative static display metrics, and effective-market denominators. It also maintains three global lists per good: origin-effective markets whose production is at least 20% of the highest production market, transit-effective markets whose export is at least 20% of the highest export market, and consumer-effective markets whose demand is at least 20% of the highest demand market; zero-value markets are excluded. Origin and transit denominators are total export across their effective lists, and the consumer denominator is total import across its effective list. Representative markets are only detail-page decision support. The yearly Trade League pulse refreshes the global cache once per year through a global version/cooldown, then each eligible Trade League leader that has not seen that version recomputes every tracked good and refills monopoly slots. The monthly pulse recomputes only goods already stored in unlocked or previously-filled monopoly slots, using `every_in_global_list` over the effective market lists rather than scanning every world market. Origin and transit control divide member export from effective markets by the cached effective total export; consumer control divides member import from effective markets by the cached effective total import. The final `tv_trade_monopoly_level_pct_<good>` is the maximum of those three percentages, capped at 100, with `tv_trade_monopoly_type_<good>` set to 1 origin, 2 transit, or 3 consumer. `tv_trade_monopoly_stage_<good>` is 0 none, 1 potential at 25%, 2 low at 50%, 3 high at 75%, and 4 complete at 100%. Annual full recalculation auto-fills monopoly slots from goods at or above 25% by final percentage descending, with YAML order as the stable tie-breaker; monthly refresh updates the existing slot values but does not reselect goods. The Trade League has 1 slot by default and 2 slots once membership reaches 10; goods outside unlocked slots are not visible and provide no monopoly action benefit. `tv_trade_monopoly_<good>` is set only when the good is in an unlocked slot and has at least 50% final monopoly progress.

The monopoly/action layer generates two slot-select actions plus one fixed selected-good action set: set virtual demand or virtual production through market + value `select_trigger`s, increase/decrease/cancel either virtual action, set an embargo through market + country `select_trigger`s, cancel the embargo, and add one node to the persistent Trade Chain. Those fixed actions dispatch by `tv_trade_selected_good` into generated per-good script branches where needed, so the GUI does not instantiate per-good buttons. Each point of virtual demand or production locks 5% monopoly level, while each embargo locks 30%. Virtual demand uses generated `goods_demand` entries and is applied as `add_temporary_demand` with `months = -1`; set/increase/decrease/cancel actions remove and reapply it as needed, monthly monopoly maintenance removes it when the monopoly is lost, and the Trade League monthly fallback removes all virtual demand while the Grand Merchant cannot maintain monopolies. Virtual production tracks `tv_trade_virtual_supply_applied_<good>`, applies `add_goods_supply` once when active, removes it by applying a negative `add_goods_supply` amount before changing/canceling/suspending, and reapplies it when maintenance conditions recover. Embargo applies a 2-month `merchant_power_severe_penalty` through `add_merchant_power`. Action variables persist on the leader country when the monopoly is lost, but effects are applied only while `tv_trade_monopoly_<good> >= 1`. Every generated action is also registered in `tv_trade_league_list.txt` and `messagetypes.txt`. The Trade League overview shows a generated strength card with distance/flow/strength values and one dynamic `ShowModifierEffect(Concatenate('tv_trade_chain_strength_display_', ...))` row, followed by chain cards: the capital market card first, existing node cards in order, and one add-node card while count is below 20. The generated Trade League custom tab shows one rectangular slot card per unlocked monopoly slot, each with a progress piechart and centered good icon, good/stage labels, final percentage and origin/transit/consumer monopoly type, plus origin, transit network, and consumer percentage rows. Selecting a filled slot refreshes the existing projected detail card and leader-only fixed action card for the selected good; the detail card keeps representative origin/transit/consumer market tables for decision support.

Manual appointment/change routes through `tv_governor_request_appointment_effect`: the capital region appoints directly, prepared non-capital regions appoint directly when any owned regional location already has `tv_govhouse_local_administration`, and missing non-capital regions save pending governor/region/location variables before firing `tv_govhouse.5`; accepting pays `tv_govhouse_local_administration_price` (400 gold, allowed to go negative/auto-loan), instantly constructs the event-only Local Administration building at the mapped owned location, then resumes appointment, while declining clears the pending state and cancels. `tv_govhouse_local_administration` is a one-level government-category support building available to all location ranks for scripted construction only: `country_potential`, `allow`, automation construction, and demolition are all disabled; it uses paper 1 + tools 1 maintenance and cannot be manually built or destroyed. The overview-level `tv_auto_assign_governors` action refreshes the region list, then repeatedly chooses one empty owned region that is either the capital region or already has `tv_govhouse_local_administration`, and the highest `total_abilities` eligible character until every prepared owned region is filled or no eligible character remains; it never opens the construction event or spends money automatically. All governor management actions require an alive Grand General in office. If the Grand General is dismissed or dies, existing governors remain appointed and continue refreshing, but no new governor can be appointed/changed/removed until a successor is appointed. **Grand General:** character leader stored as the independent country variable `tv_conquest_general_char`; managed via generated Appoint/Remove/Change IO leader actions and displayed in the IO header. Newly appointed Grand Generals initialize `tv_gg_loyalty` on the character if absent (nobles 0%, burghers/clergy 10%, crown 30%, other estates 20%); the value is mirrored to `tv_gg_loyalty_value`, does not drift automatically, and lowers the Governor's House power-balance equilibrium by the same amount. A monthly 5% loyalty pulse can fire one of three events: -5 loyalty, +5 loyalty, or a reward demand costing `scale = 1` gold for +5 loyalty with refusal causing -5 loyalty. `tv_govhouse_authority` IO variable (0-100, monthly decay × 0.0005, grows by Grand General's mil × 0.05). The Governor's House overview tab renders the display-location list: each row shows a region icon/name, the separate integration slot, right-aligned ADM/DIP/MIL function entries with formula tooltips, and the current governor as a standard `io_character_card`; Assign/Cancel/Change Governor buttons still pass the row's region scope. The dedicated Grand General tab shows the current variable-backed character, active training progress below the character card, authority value, Appoint/Change/Remove actions, and the existing Train Grand General action.

Governor automation note: `tv_enable_governor_automation` / `tv_disable_governor_automation` toggle the country variable `tv_govhouse_governor_automation_enabled` from the overview `button_checkbox_auto` checkbutton beside `tv_auto_assign_governors`. When enabled, governor death, manual removal, location ownership changes, governor country moves, a governor becoming ruler, and marriage/royal-marriage cases where a governor becomes a consort each run one guarded `tv_govhouse_auto_assign_if_enabled_effect` pass; that helper delegates to `tv_governor_auto_assign_effect` only while a living Grand General is available, so the automation does not rely on monthly polling.

Governor assignment country note: new Local Governor assignments store `tv_governor_country` on the character so event-driven vacancy cleanup can find the original appointing country even if the character's current owner changes.

Governor autonomous task note: `tv_governor_select_yearly_task_effect` sets one active task per regional governor. The six tasks are restore prosperity, integrate region, convert culture, convert religion, strengthen recruitment, and strengthen order; integration is one of these autonomous tasks, not a separate always-on governor modifier. The task values scale from ADM/DIP/MIL, are displayed through `tv_govhouse_display_task_type/value`, and are refreshed into region-wide location modifiers by `tv_governor_apply_modifiers_effect`.

Regional Governor random events: `tv_govhouse_governor_events_monthly_pulse` runs through the generated `monthly_country_pulse` registry and only triggers if at least one living governor has an owned governed region. It uses a single monthly country-level roll with 180 no-event weight plus 20 event weights, giving a 10% total monthly chance. Events `tv_govhouse.100`-`.119` each pick one random eligible governor in `immediate`, save the governor, governed region, and a representative owned location as event scopes, then apply one-year region-wide location modifiers and/or immediate or one-year country effects. The 20-event set covers two-choice good events, one-option good events, two-choice tradeoff events, two-choice bad events, and one-option bad events.

Governor's House laws: the IO uses the vanilla IO Laws tab. Six generated core law groups (`tv_govhouse_expedition_goal_law`, `tv_govhouse_governor_appointment_law`, `tv_govhouse_local_autonomy_law`, `tv_govhouse_religious_mission_law`, `tv_govhouse_frontier_military_law`, `tv_govhouse_imperial_integration_law`) each have four effect-bearing country policies. `tv_govhouse_grand_general_power_law` sits in the new `tv_govhouse_grand_general` category: Marching Orders gives newly appointed Grand Generals +10% initial loyalty, Garrison Orders makes governor task/function effects 20% stronger, and Supreme Command gives newly appointed Grand Generals -10% initial loyalty while doubling General Tactics and War Plan progress gain. Four generated Local Governor Function laws sit in `tv_govhouse_governor_functions`: the ADM/DIP/MIL function laws decide which scaled local modifiers governors apply, while `tv_govhouse_governor_duty_tendency_law` adds +0.30 task-selection weight to one of the six autonomous governor tasks. Every generated policy has a data-driven AI base vote bias from -60 to +60 in 20-point steps, favoring subject-friendly, traditional/conservative, and profit-seeking choices; when a policy is the current proposed law target (`ai_io_law_target`), the AI also adds opinion of the IO leader scaled from -200..+200 opinion to -100..+100 vote bias plus +5 vote bias per leader diplomatic reputation. All eleven laws keep `requires_vote = yes`, `has_parliament = no` hides the separate IO Parliament tab, and the IO starts with no initial policies. There is no monthly default-law backfill.

Governor's House War Tent: requires an alive Grand General. The custom War Tent tab has three units: General Tactics, War Plan, and Main Actions. On war entry, `tv_govhouse_war_entry_effect` proposes one random tactic from the eleven-tactic pool and fires `tv_govhouse.40`; the player approves or rejects it. While continuously at war, the monthly pulse has a 5% chance to propose a replacement tactic, excluding the tactic already active. Approved tactics are applied as country-scoped static modifiers and are cleared when the country leaves all wars or loses its Grand General; this approximates general tactics because the army-wide combat modifiers did not apply reliably from the stored character path. Supreme Command doubles the applied tactic modifier size, including the Capital Raid location modifier. War plans are mutually exclusive: offensive plans select a target country and, while at war with that target, scale Siege Ability by progress x 0.2% and Discipline by progress x 0.1%; defensive plans need no target and, while in any defensive war, scale Fort Defense by progress x 0.2% and Military Tactics by progress x 0.005. On war entry, applicable offensive/defensive plan bonuses are activated through `tv_govhouse.41` / `tv_govhouse.42` events instead of being granted directly by the war-entry effect. Plan progress increases monthly by Grand General adm x 0.02 up to 100, doubled under Supreme Command; aborting/changing target resets it, and peace with an offensive plan target aborts that plan.

Governor's House header action note: `tv_govhouse.gui` adds a fixed-size semi-transparent Grand General Actions card to the IO header. It displays, in priority order, the appointed Grand General's commanded army link, wartime tactic planning, peacetime subject-annexation assistance, peacetime inspections, or the no-Grand-General fallback. The peacetime annexation row is driven by the country cache `tv_govhouse_annexing_subject_active`, refreshed by `tv_govhouse_update_general_action_display_effect` from the existing monthly War Tent path so the GUI does not scan subject diplomacy directly.

8. **Global Victory Leaderboard** — Monthly per-path ranking of the top 5 countries for each victory path. `tv_update_leaderboard_effect` writes situation variables `tv_<path>_rank_1_country` through `tv_<path>_rank_5_country`; the Victory Situation page for the selected path displays those countries with flag, country name, the selected path circle icon, that path's milestone count, and that path's score text.

Governor's House eligibility/death note: new governors and Grand Generals exclude female characters and artists at the selection/action-effect entry points. There is no monthly legacy-eligibility cleanup, to keep the IO monthly path focused on active governor bonus refresh. `tv_govhouse_governor_death` is registered under `on_character_death`, fires `tv_govhouse.1`, removes the dead governor from `tv_governor_list`, clears their region modifiers, and rebuilds the display lists immediately.

Grand General training note: `tv_train_grand_general` applies the one-year `tv_grand_general_training_modifier` country modifier defined in `src/in_game/common/static_modifiers/tv_govhouse_modifiers.txt` (`court_spending_cost_modifier = 0.10`), tracks `tv_gg_training_months` on the Grand General via monthly pulse, mirrors it to the country-side GUI display variable `tv_gg_training_progress`, resolves at 12 months through `tv_training_resolve_effect`, and routes to skill gain, trait-path upgrade, injury, or death events before clearing state.

Grand General death notification note: natural Grand General deaths trigger `tv_govhouse.2` from `tv_govhouse_char_death`; training-caused deaths set `tv_gg_training_death_notified` before `kill_character = this` so the already-shown training death event is not duplicated.

Governor's House balance-of-power backlash note: `tv_govhouse_power_balance` is an IO variable in the 0..1 range and is checked monthly by `tv_govhouse_negative_monthly_pulse` (registered through `data/pulse_registry.yaml`). `tv_govhouse_power_equilibrium` recalculates monthly from a -20% base, the Grand General's share of combined ruler/general abilities, `tv_govhouse_power_consolidation`, and a subtraction equal to the mirrored Grand General loyalty value; `tv_govhouse_power_balance` then moves toward that equilibrium by up to 0.6% per month. Below 25% no backlash events fire. At 25%/50%/75% the pulse uses a single `random_list` roll with a 300 total weight so at most one backlash event can appear per month, and each eligible event has weight 1/300. Events `tv_govhouse.10`-`.13` are tier 1, `.20`-`.25` are tier 2, and `.30`-`.34` are tier 3. Every backlash event has exactly two options: accept the negative effect, or pay an alternative resource and call `tv_govhouse_reduce_power_balance_effect` to lower the balance by 5 percentage points. Tier 2 adds rare art/artist losses; tier 3 upgrades the local satisfaction loss to an area-wide effect and adds a cabinet crisis. The Governor's House GUI shows right-aligned fixed-width 25/50/75/100% markers and four warning rows below the Balance of Power bar for the <25, 25-49, 50-74, and 75-100 segments.

Grand General replacement cost note: generated Remove/Change Grand General actions call `tv_govhouse_pay_grand_general_replacement_cost_effect` before resetting `tv_govhouse_power_consolidation`; the cost is Government Power equal to `tv_govhouse_power_consolidation * 20`, so a fully consolidated Grand General costs 20 government power to remove or replace.

## IO Architecture Design Decisions

The character-led TV IOs (`tv_arts_exhibition`, `tv_diplomatic_alliance`, `tv_academy_of_sciences`, `tv_govhouse`, `tv_engineering_department`, `tv_trade_league`) share invariants that must never be broken.

### 1. leader_country = founding country, locked at creation

`on_creation = { set_leader_country = scope:actor }` runs once when the IO is created. `leader_country` is not reassigned by normal gameplay afterward; the only exception is the manual recovery action `tv_reinitialize_mod`, exposed at the top of the Victory Situation panel, which recreates missing victory-path IOs where possible and reassigns joined TV IO instances back to the current country. It controls IO permissions, `is_leader_of_international_organization` trigger, and `leader_country.modifier:` chained access in `monthly_change` scripted values.

### 2. No elections — leader_change_trigger_type = none is mandatory

All TV character-led IO type definitions keep `leader_change_trigger_type = none` and `leader_change_method = none`. These prevent the engine from reassigning `leader_country` automatically. `international_organization_chooses_new_leader` is **globally banned** from all TV IO-related code — this effect triggers the vanilla election process. Any call to it violates the no-elections design and risks silently reassigning `leader_country` to a different country.

### 3. Great person characters are independent country variables, not the vanilla ruler

The character displayed in the IO header is stored as a country variable on the `leader_country`:
- Arts Exhibition: `tv_arts_exhibition_leader_char`
- Diplomatic Alliance: `tv_diplomatic_alliance_leader_char`
- Academy of Sciences: `tv_academy_leader_char`
- Governor's House: `tv_conquest_general_char`
- Engineering Department: `tv_great_engineer_char`
- Trade League: `tv_grand_merchant_char`

These are set/cleared exclusively by the generated generic actions in `tv_io_leader_actions.txt`. The vanilla `leader_country.GetGovernment.GetRuler` and `appointed_leader.*` are different concepts and must not be used in TV IO calculations.

### 4. IO variable monthly_change uses chained character attribute access

All IO variable `monthly_change` scripted values that depend on the appointed great person must use `leader_country.var:tv_xxx_leader_char.attribute` chained access — never `appointed_leader.attribute`. Examples:
- CORRECT: `value = leader_country.var:tv_academy_leader_char.adm`
- FORBIDDEN: `value = appointed_leader.adm`

### 5. IO monthly_effect blocks are forbidden

TV international_organization type definitions must not use `monthly_effect` blocks. IO monthly effects have severe performance costs even when hidden. Keep visible typed-variable monthly arithmetic in each variable's `monthly_change`; route maintenance, completion checks, and side-effect work through registered country monthly pulses or explicit lifecycle hooks.

### 6. Header display uses blockoverride

All character-led IO panels use `blockoverride` on their header template to display the appointed character (read from the country variable via `GetPlayer.MakeScope.GetVariable(...).GetCharacter`). Never use the vanilla `GetLeaderCountry.GetGovernment.GetRulerOrRegent` accessor chain.

### 7. All TV IOs have unique = no

Each country pursuing the relevant victory path creates its own independent IO instance. The `international_organization:type_name` scope link is **invalid** for non-unique types. Always use `every_international_organizations_member_of = { limit = { international_organization_type = international_organization_type:<io_type> } ... }`.

## AI Workflow Knowledge

AI workflow state is maintained as project source, not by manual human follow-up. `scripts/ai_context.py` builds the task-scoped context from changed or explicit files, generated-file metadata, `docs/knowledge/anti_patterns.yaml`, short domain risk cards in `docs/knowledge/risk_cards/`, and content markers for `variable_map` / `global_variable_map` / `local_variable_map` usage. Current registered risk cards: `events.md`, `generic_actions.md`, `gui.md`, `international_organizations.md`, and `on_action.md`; event files route to the events card because option tooltips can pre-evaluate option effect chains, including `hidden_effect`, while IO definitions, IO laws, and country interactions that find or mutate TV IOs route to the international-organization card because IO scopes are high risk. Files containing variable-map content route to the local Variable maps documentation and prioritize the `variable_map_scope_link_used_direct_rhs` anti-pattern because direct quoted map lookups are unsafe as RHS/effect parameters. Anti-pattern entries use `detectability` to distinguish safe regex lint (`lint`), parser/semantic rules (`needs_parser`), and AI-facing warnings (`advisory`), and may name a semantic `validator` implemented in `scripts/validate.py`. `scripts/validate.py` enforces safe lint rules, emits generic-action pre-evaluation and interaction-target chooser warnings, rejects visible generic-action calls to registered hidden-only cleanup helpers, emits IO policy AI-scope warnings/errors, fails duplicate main-menu localization keys within the same language pack, rejects dotted event references whose numeric event ID is `>= 10000`, rejects direct `effect = { ... }` child blocks inside event options, walks `monthly_country_pulse` registry callbacks and TV helper calls to require the configured one-day event delay, checks that risk cards remain registered in `ai_context.py`, checks that each TV IO type has a matching `main_menu/gfx/interface/icons/international_organizations/<io_type>.dds` GetIcon asset, rejects TV IO `monthly_effect` blocks, checks that generated main and M&T compatibility `location_window.gui` outputs match their current generators/reference inputs, and checks that TV does not stack a second direct `effect` onto hardcoded vanilla on_action hooks such as `on_annex` or `on_winning_war`. `scripts/test_lint_rules.py` runs fixture tests from `tests/fixtures/anti_patterns/<rule_id>/` for selected lint regexes.

All AI workflow command examples distinguish normal user terminals from managed sandboxes. In Codex, Claude subagents, or other managed sandboxes, project Python scripts are run with `C:\Users\Hades\anaconda3\envs\eu5\python.exe scripts\...`; agents must not run or retry `conda run -n eu5` there because the read-only Anaconda base metadata path can make it hang. The `conda run --no-capture-output -n eu5 python ...` form is reserved for normal user terminals and generated `Regen:` documentation lines. `scripts/ai_context.py` prints managed-sandbox validation suggestions with the direct interpreter form.

For Engineering Department wonders, remember the noncapital building rule: EU5 building `modifier` / `raw_modifier` are local, while `capital_country_modifier` only applies country effects if the building is in the capital. Since wonders can be outside the capital, final wonder buildings keep base national/global effects in their `modifier` block only as display data; the real base country effects are generated as level-gated Country Auto modifiers, while real ritual country effects are applied as static modifiers when the selected ritual completes.

Generated files that copy vanilla sources preserve the copied vanilla content verbatim except for explicit TV insertion points. The on_action bridge registry generator emits one TV-owned bridge file, `tv_pulse_bridges.txt`, containing shared parent hooks such as `monthly_country_pulse`, `yearly_country_pulse`, `on_character_death`, `on_ruler_death`, startup/load hooks, war hooks, subject hooks, ownership hooks, institution-embraced hooks, capital-moved hooks, and CMF callbacks. Those blocks register only TV-owned callbacks through `on_actions = { ... }` and let vanilla or feature files provide the rest of each hook body. The bridge file must not use vanilla filenames such as `country_monthly.txt`, because those collide with vanilla files and can replace rather than extend them. Feature on_action files should keep only named `tv_*` callback bodies; parent hook bridge registration belongs in `data/pulse_registry.yaml` and generated `tv_pulse_bridges.txt`. The only intended vanilla-copy insertions are TV character title entries from `data/io_leaders.yaml` and TV message type entries from `scripts/gen_messagetypes.py`. `data/pulse_registry.yaml` owns the bridge on_action names and `settings.monthly_country_pulse_event_delay_days`, currently 1; any TV event whose conditions are checked by a `monthly_country_pulse` callback must use `days = 1` on direct `trigger_event_*` calls or `delay = { days = 1 }` before native `events` / `random_events` ids.
